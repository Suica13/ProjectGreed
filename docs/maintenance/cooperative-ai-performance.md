# 合作任务与雇佣兵战争：AI 调度与性能验证

日期：2026-11-14，基于 V121 工作区。本轮未发布新版本。

## 原因与处理

AI 原先在一次调度中完整计算某个单位的候选移动、寻路和攻击收益。较长决策占住离线客户端的主线程，即使总计算量不大，也会阻塞绘制。现在将搜索改为可暂停的生成器，在候选位置、敌方目标和每16个寻路节点间交还执行权；服务端调度以4ms为软预算，仍会校验房间、revision与战局对象，避免过期搜索提交动作。单个不可分割操作仍可能超出预算。

同时跳过超出所有武器射程的攻击评分，移除重复的战场AI调用。同步接口保留，方便原有调用及结果对照。没有复制客户端裁定或改变命中随机结果。

首次输入原本会遍历并解码整套战斗音效。现在只预热当前参战型号，解码并发最多2个，并按音频来源复用缓存；按钮与新出现的音效按需加载。停止或切换场景会使未完成的播放请求失效。任务目标文字在内容未变化时复用现有节点。

雇佣兵战争按单位当前位置选择最近的敌方／中立据点；敌方HQ更近时优先HQ。不能压制的单位攻击守军或HQ。增援优先支援受威胁地点，否则优先最靠近敌方HQ的己方据点，落点满员后回退。任务与雇佣兵战争不再为额外集结或等待附近低EN乘客而停留；正常编队、搭载与补给功能保留。

## 本机测量

Edge 157 无头浏览器，同一台机器、相同62单位战场、25%缩放、5秒采样。数值是CPU与帧间隔测量，不能等同于安卓真机或不同显卡的FPS承诺。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 最长AI执行段 | 45.6ms，完整决策 | 3.3ms，搜索片段 |
| 最差帧间隔 | 83.4ms | 34.7ms |
| 浏览器长任务 | 4次 | 0次 |
| 平均绘制耗时 | 1.41ms | 1.32ms |

延长至20秒、推进到第3回合后，最大搜索片段7.2ms，仍出现一次55ms长任务，最差帧间隔55.7ms。因此本轮改善了AI计算造成的连续阻塞，尚不能认为所有卡顿已经消除。任务模式我方闲置回合在本机未复现持续掉帧：前后均无长任务，最差帧间隔约7.1ms；音效加载与重复目标刷新属于已确认的额外工作来源。

原始性能报告保存在 `tmp/verification/reports/`：`mercenary-scene-before.json`、`mercenary-scene-after.json`、`mercenary-soak-after.json`、`mission-live-before.json`、`mission-live-after.json`。早期 `mercenary-live-before.json` 停留在房间页面，不作为战场前后对比依据。

## 验证范围

- 55项相关Node规则、AI调度与音频测试通过。
- 11项调度、公平性及真实WebSocket任务／雇佣兵战争测试通过。
- 8项相关浏览器测试通过：桌面／手机设置、选择性音频加载、按钮音效，以及任务对话头像、镜头锁定和恢复操作。
- 原有移动音效浏览器用例仍引用旧列表入口／音效图层，未作为本轮通过项；未为适配旧断言修改现行表现规则。
- 未进行安卓真机、长时间公网多人或全量历史测试验收。

前期、中期、后期现为1～30、31～70、71～100回合；任务预算2000，任务禁用标签隐藏且由服务端忽略；客户端分类名称统一为合作模式。常规网页构建已更新，未执行原生客户端发行打包。

## 2026-11-15：多人广播、界面与贴图复用

3v3、300单位、关闭迷雾的固定负载中，服务端广播及网络状态编码的重复工作比单次AI搜索更显著。内部AI席位原先也接收完整快照；现在仅向人类玩家与观战者发送。每次广播按队伍复用已经过滤的单位视图，个人预备库存仍单独筛选并移除模板。只在只读视图生成期间复用派生属性，不将缓存跨越战局裁定或下一次广播。

增量编码使用不可变JSON字符串保存基线，优先比较整台单位，仅拆分发生变化的单位字段；不再先解析整份快照后逐字段重复序列化。一次同步广播内可以复用相同对象的JSON结果。发送队列冻结慢连接的快照后不携带该缓存，避免下次单位变化污染基线。旧客户端完整快照和现有增量协议均保留。

客户端按驾驶员实际属性及经验加成复用派生机体数据，缓存全局最多4096项，不依赖每次解码产生的新驾驶员对象。资源集合按实际单位、交战与特效引用缓存，避免遍历库存、头像和整张地图。行动与范围缓存使用服务端revision失效；信息面板只保存真实滚动容器及展开项，不再读取每一个文字节点的滚动坐标。地图和战斗列表中的可控单位血条统一为绿色，包含共享控制的友军。

正常缩放只缓存骨骼和身体帧完全静止的原分辨率身体；变化中的骨骼、身体序列帧、战斗演出和特效仍按当前时间绘制，不使用12FPS替代。光照过渡期间走实时路径，避免每帧生成不同光照的缓存。已有像素、条目与每帧烘焙预算继续生效。

同机Edge、1920×1080、300单位、3v3、40次快照的CPU测量如下。客户端负载包含逐次快照处理及绘制，并非公网延迟或安卓GPU帧率保证。

| 平均耗时 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 服务端一次广播 | 54.6ms | 18.7ms |
| 每名接收者增量编码 | 4.5ms | 1.2ms |
| 客户端无选择快照刷新 | 13.1ms | 5.8ms |
| 客户端选中单位快照刷新 | 17.8ms | 8.8ms |

可复用工具：`node tools/performance-multiplayer.cjs --players 6 --units 300 --samples 40 --output tmp/verification/reports/multiplayer.json`。支持2／4／6／8／10名玩家和`--fog full`，同时输出服务端及浏览器CPU采样。基准原始数据为`tmp/verification/reports/multiplayer-before.json`与`multiplayer-final.json`；另有5v5迷雾压力样本。该工具不进行真实公网延迟测量；真实WebSocket的3v3测试验证独立库存、完整／增量客户端混用及连续广播同步。
